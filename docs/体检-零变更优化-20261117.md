## 0. 一句话

**最大问题不在"优化"，而在一个 bug**：导出笔记时把整个微软雅黑字体（约 11.8 MB）嵌进 PDF，导致「附笔记」版本比原讲义大 6–8 倍。已修（`ui\server.py` 两行），实测 12.44 → **0.82 MB**（−93%），**逐页像素 0 页不一致**。

## 1. 已修（本轮唯一改码）

| 项 | 改前 | 改后 | 证据 |
|:--|--:|--:|:--|
| 合订本 · 附笔记 | 16.78 MB / 146 页 | **5.04 MB** / 146 页 | 全文本哈希一致 |
| L01 · 附笔记 | 12.44 MB / 21 页 | **0.82 MB** / 21 页 | 全文本一致；**逐页像素 21/21 一致**（100 dpi 渲染逐页比 sha256） |
| L03 · 附笔记 | 13.15 MB | **1.42 MB** | 全文本一致 |

定位过程（可复跑）：
1. `pymupdf` 压缩参数不是原因：`garbage=4 + deflate + deflate_fonts` 只从 16.78 → 16.70 MB；
2. 逐个流对象量体积 → **单个流 xref 11.80 MB**（合订本附笔记），原讲义同对象不存在；
3. 原因：`build_note_pdf` 用 `insert_text(..., fontfile=msyh.ttc)`，PyMuPDF 把整个字体文件嵌进去，实际只用到几百个字形；
4. 修法：`doc.subset_fonts()` + `save(garbage=4, deflate=True, deflate_fonts=True)`，失败时 passthrough，不影响出件。

**存量 4 份「附笔记」PDF 未重导**（重导会用当前笔记内容覆盖，等用户决定）：按实测比例，四份合计约 54.8 MB → 约 8 MB，**省约 47 MB**。

## 3. token

- 问课件的提问包实测 **1,280 字符**（TOP_K=5 × 420 字符 + 节号页码），检索耗时 **< 1 s**，不花钱模式可用。
- 结论：**没有可压的空间而不改回答质量**。压 TOP_K 或段长会改变给模型的证据集 → 属于改行为，不算零变更。
- 可做的只有「重复问题响应缓存」（顾问建议 ②-2），但会返回旧回答作为新回答，风险高于收益，本轮不做。

| 项 | 现状 | 建议 |
|:--|:--|:--|
| 检索 | 线性扫「节→块」词命中打分，TOP_K=5 | 166 页规模下 <1 s，**倒排索引没有必要**（顾问建议收益在这规模不成立） |

## 5. 逻辑

- 增量构建（顾问建议 ④-1）：单讲 7 s，收益也就是 7 s → 4 s，且引入「指纹漏项复用旧产物」风险。**不建议**。
- 但有一条真收益：`_make.py` 单讲跑完会顺手把 9 份全部校验一遍（实测 7 s 里含这段），若只校验变更讲，可再省一部分——属**未验**，未做。

---

## 6. 架构

**可做（收益明确、风险低）：静态资源加 ETag + 304**

- 现状：`ui\server.py` 里 JSON 与文件一律 `Cache-Control: no-store`（L437 / L454 / L482），`favicon` 才 `max-age=86400`（L512）。
- 后果：每次打开/刷新都重传 `pdf.worker.min.mjs` 1.33 MB + `pdf.min.mjs` 328 KB + KaTeX 269 KB ≈ **2 MB**（本机无感，平板走 WiFi 时明显）。
- 改法：对 `tools\print\pdfjs\*` 与 `tools\print\katex\*` 回 `ETag`（文件 sha256 前 16 位）+ 支持 `If-None-Match` → 304；`index.html` 仍 `no-store`（避免旧界面）。
- 验证：首次 200 的 sha256 与文件一致；第二次 304；界面与渲染无变化；`index.html` 仍不缓存。
- 回滚：去掉 ETag 分支。
